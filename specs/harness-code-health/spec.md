# 基于现行契约的代码治理 GC

## Summary

代码治理是 Harness 的第三类来源。Main、Plan、Coding、Test、Review 共用同一运行器、
预算、工作区、工作流与交付。Agent 自主调查全仓，一次选择一个连贯主题形成一个 PR。

## Design

任务冻结远端 main、源码索引、黄金原则及现行 SDD。Plan 的发现包含原则引用、源码
片段、影响、验收依据、调查范围和未决项；非确定性推测不能成为自动清理的依据。
只允许现行产品范围内修改，现有测试、依赖、权限、规则与规格保持固定。

验收用途由宿主按来源确定：故障修复继续要求有效失败对照；GC 可以从全绿基线开始，
但须有绑定冻结目标的前后改善证据、行为与保护集验证及独立审查。缺失证据不交付。
没有可执行发现为 no_changes；仅敏感项为 needs_review；调查未完成不得宣称全仓健康。

复用 AcceptedCandidate 与 PR 对账，主干前进重新检查目标、回归与审核。来源、控制、
运行适配与 UI 遵守既有六层依赖。新增来源沿用 pipeline 9，不清空状态库或复活旧协议。

定时默认关闭，默认间隔 24 小时，启用时冻结明确的模型与预算。systemd 用户 timer
只创建普通治理任务；已有活动治理或未完成交付时跳过，不积累任务。模型不能控制调度。

## Acceptance

- 全绿基线可以完成有证据的 GC，业务修复仍要求失败对照。
- 治理依据与改善证据绑定真实源码；无发现、敏感项和调查缺口正确区分。
- 角色权限、累计预算、取消、恢复和交付复验复用现有 Harness。
- 手动和定时共用去重，定时默认关闭；任务、产物与命令日志均可追溯。
- 操作者工作区、历史归档和原始测评记录不变。

## Verification

来源、发现、验收、并发去重、调度、取消与交付定向测试；前端测试、构建和界面检查；
随后 full 检查。固定 GC 样本运行真实 Agent，初次禁用发布，分别记录模型与交付证据。
