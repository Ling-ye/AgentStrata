# 基于现行契约的逐项代码熵回收

## Summary

代码熵回收是 Harness 的第三类任务来源。每项使用同一运行器、角色、工作区、验收与交付。
一次回收可按累计执行时间或问题发现数停止，但始终发现一个问题后立即修复、验证并提交 PR，
确认合并后再开始下一项。问题的修复尝试上限与整次回收的停止条件分别计量。

## Design

每项冻结最新远端 main、源码索引、黄金原则及现行 SDD。Plan 的首个有效发现包含规则引用、
源码片段、影响、范围与验收目标；宿主限定每项最多一个 finding，并冻结问题供返工使用，
不接受额外回收提示或人工预期。非确定性推测不能成为自动清理依据。

整次回收以轻量批次记录保存在现有 Harness 数据库，子任务仍使用既有任务、尝试与证据记录。
批次负责停止条件、顺序推进、计数与取消，不能越过子任务验收或交付。当前 PR 已合并且
实际执行停止后，以稳定批次和序号身份创建下一项，从最新 main 重新冻结源码和规则。
无发现提前结束；人工判断、修复失败和交付阻断停止整次自动推进。

按时间默认累计执行 3600 秒，跨问题共用；准备、调查、修复、验证与交付复验计时，纯等待
和状态轮询不计时。耗尽停止主动执行，保留证据，已发布 PR 仅核对状态和收尾。按发现数默认
1 项，不附加时限；发现计数与完成计数分别保存，达到上限仍完成当前项。每项默认最多 3 次
修复尝试（含首轮），恢复不能重置预算或计数。取消先持久化批次意图，实际收尾后才完成。

公开批次入口为 `/api/harness/code-health/runs`（创建、分页、详情、取消、恢复）；参数
stop_condition 是 `{mode: time, seconds}` 或 `{mode: findings, count}`。Console、CLI、定时
共用新契约，不再接受 single_issue、repair_hint 或直接从普通修复创建入口启动 GC。
定时默认关闭、间隔 24 小时，有活动批次或未完成交付时跳过。现有分钟级交付入口负责推进。
旧参数不兼容转换，旧定时需重新保存，旧任务保留只读；新存储结构增量建立，沿用 pipeline 9。

职责遵循[六层依赖](../domain-layered-dependencies/spec.md)和[四层运行时](../runtime-four-layer-definition/spec.md)：
Types 定义批次输入和执行端口，Repo 保存记录，Service 判定顺序与预算，Runtime 装配既有
worker 与交付，UI 仅调用公开入口。不另建数据库、通用编排引擎或另一套发布权限。

验收用途仍由宿主来源决定：故障修复要求有效失败对照；GC 允许全绿基线，但必须有绑定冻结
目标的改善、行为保持与独立审查证据。既有测试、依赖、权限、规则与 SDD 固定，角色不能改
验收标准。复用 AcceptedCandidate 和 PR 对账，主干前进须复验，不更新操作者本地 main 或部署。

## Acceptance

- 两种模式均发现一项后完成其修复与 PR 合并，再发现下一项，不批量攒问题。
- 有效发现、已合并项和每项尝试分别计数，重试与恢复不重复计数、不换题。
- 时间跨项累计、纯等待不计时；数量模式无隐含时限；预算耗尽不能继续主动复验。
- 无发现、敏感项、修复失败、交付阻断及取消正确停止批次，保留候选与证据。
- 并发、回执丢失与重启不重复创建子任务或 PR；同仓库最多一个活动批次。
- 全绿基线允许有证据的治理，业务修复仍保留失败对照；权限和验收边界保持有效。
- Console 提供批次进度和子任务证据；旧字段被拒绝，历史记录不清空。

## Verification

使用受控多问题、worker 与 GitHub 回执验证顺序、计数、最新 main、幂等与取消；可控时钟验证
累计预算、恢复和等待。覆盖真实单问题验证流程、API 与 CLI 参数、调度及普通修复回归。
前端执行测试、构建及桌面/窄屏界面检查，随后执行 full。模拟回执不视为真实远端交付证据。
