# 本机 Agent 应用工作台

## Summary

工作台以“通过对话创建、运行和改进 Agent 应用”为目标，复用现有引擎、接口、Console、Harness 和 Eval，不引入第二套运行体系。Windows 入口启动 WSL2 内的本机工作台。开发对话和每个项目的源码、任务、产物在本机保存。一段对话绑定一个应用，开发请求从该项目的当前版本进入既有 Harness 和 Evaluation。业务应用通过自己的 BotSpec、Agent profile 和 Gateway 运行。

## Design

### 统一应用工作台与渐进整合

产品概念分为 AgentStrata 引擎、AgentStrata Studio 工作台、AgentStrata Apps 应用和组件四层。应用类型描述用途，应用实例拥有用户名称、配置、运行与历史；插件、渠道适配器、Skill 和 MCP 工具是实例使用的组件，不因展示命名改变持久标识或协议。Studio 作为统一工作台的产品入口，Console 的 React、Arco 和 Query 前端承载管理界面，逐步纳入创建和改进对话。旧高级入口在迁移期间保留，不通过 iframe 建立第二套控制面。

分阶段实施顺序：

1. 聚合仓库、Studio 与组件暴露的应用，建立带来源的稳定身份、能力和运行引用。相同源码配置路径只出现一次，优先保留拥有控制权的来源；状态来源失败不能变成空的成功列表。
2. 以“我的应用、创建应用、模型与连接、高级管理”组织统一前端。每个应用有稳定地址，展示概览、使用、配置、记录和改进；操作按能力显式启用，旧入口继续可达。
3. 将支持的配置、检查、启停及管理对话接入统一应用接口，委托既有管理器，不新增运行引擎或双重服务控制。试聊仅在身份和无外部投递边界验证后开放；外部客户端只展示实际可用入口。
4. 用应用身份关联现有记录、Eval 和 Harness，保持候选、独立接受与显式启用。按应用预选的高级入口是渐进整合，不等于所有来源已支持同等的测评与版本管理。

应用目录是薄的聚合视图，不复制 BotSpec 或业务数据。稳定身份由来源与原有 ID 构成；名称不是定位依据。实例引用、管理项目引用和能力独立记录，组件自身不重复作为应用展示。Studio 的标准应用由原 ApplicationManager 管理，仓库实例沿用 Console 的原有控制路径，插件暴露的只读实例不能因新页面得到额外控制权限。

“使用应用”与“改进应用”是不同上下文：前者属于业务 Gateway 会话，后者属于管理项目与开发任务。管理模型只获得用户明确输入及允许的应用配置摘要，不能读取完整私有配置、凭据或环境。前端请求、Query key、草稿与消息均绑定稳定应用身份，切换后迟到响应不能显示在另一应用。进程、渠道连接、端到端交付分别展示；未验证状态不能通过显示名称推断为成功。

### 应用范围验收

- QQ 工作台试聊使用独立 Gateway user 客户端，工具白名单为空；会话与管理对话、QQ 渠道会话分离，试聊不产生 QQ 投递。旧进程缺少专属凭据时不能退回 owner 身份。
- 试聊使用公共 Gateway run 身份契约；持久请求 ID 不可跨应用或改写内容，未知结果先查询，明确不存在才允许用户用原 ID 重试；终止请求与终态分别显示。
- 仓库应用的 Eval/Harness 历史由服务端解析精确实例身份，筛选先于分页。Studio 仓库外应用不通过放宽源码边界获得这些能力。
- 桌面构建下载复用原产物校验：项目与消息必须匹配、构建就绪、摘要一致。不把下载或打开安装包表述为启动已安装应用。
- 新桌面构建的受信发布程序记录完整启动程序及资源清单，回执绑定清单摘要、安装 ID 和运行源码。统一使用页只能通过固定本机选择器绑定实际安装，核对文件归属、写权限、无重解析点、完整文件摘要与运行版本；校验时持有文件的只读共享句柄。请求不接受任意路径或命令，不因显示名称或历史启动记录推断安装位置。旧构建缺少清单时拒绝绑定。现有准备流程未产出可信的已解包依赖清单，因此启动在 UI、BFF 和原生脚本均拒绝；绑定不等于完整运行环境可信。

### 桌面运行依赖的后续信任条件

启用统一启动前，受信 provisioner 必须从已绑定摘要的 Python 发布归档、wheel、插件和 MCP
下载物派生完整执行文件集合，覆盖解释器、DLL、site-packages、启动脚本、插件运行环境及
生成的路径配置。派生应在全新隔离目录完成，不执行既有安装中的 Python 或复用未经重新
核验的缓存；只允许由可信输入及确定性转换得到的成员，生成项须记录转换版本与输入摘要。
构建/部署回执须将这些结果与 launcher、应用源码、安装身份绑定，用户配置和业务数据
保持独立。启动前同时校验完整成员集合、摘要、路径归属和无额外可加载代码，并处理
依赖更新后的显式重新验收。安装端自行生成的 JSON、artifacts_digest 标记、以及首次绑定
时给现有环境拍摄的摘要都不是独立可信依据。当前未实现该链路，不能宣称统一桌面启动完成。

### 标准应用装配与运行

工作台分开处理配置操作与源码开发。标准应用以现有 BotSpec、Agent profile、模型绑定和 Channel 接口装配；配置、检查、启动、停止不创建 Harness 任务，也不要求开发 worker 认证。新增接口、工具或业务逻辑才进入既有候选与独立验收流程。模型 API 可以服务标准应用；Harness 当前仍使用 Codex 开发 worker，不能从聊天模型已连接推定开发能力就绪。

首个标准应用类型是 QQ 官方机器人，与已有 QQ / NapCat 的 OneBot 渠道分开。渠道只处理官方认证、事件与投递；身份、准入、上下文和 Agent 能力继续按[四层运行时基线](../runtime-four-layer-definition/spec.md)归属，工作台和生命周期管理位于消息链之外。普通用户不接触 YAML，开发者与 UI 使用同一组确定性应用操作，不让对话模型直接生成 Shell 命令部署。

同一页面组合聊天与连接卡。聊天提出名称和回复要求等配置建议，用户明确应用后持久化；AppSecret 由专用表单输入，不进入聊天、模型上下文或导出物。只给模型及前端返回脱敏状态。请求目标固定为当前应用，启动、停止和重试保持幂等；已有项目记录不因增加应用类型而改写或迁移到另一个应用。

用户自行拥有 QQ 平台账号和机器人，并按平台要求配置权限和测试成员。MVP 仅提供本机运行，不创建平台账号、不代办审核、不自动公开上线或云托管。配置检查、进程运行、官方平台确认和真实消息往返分别取证；不能用本地校验或进程存活表示“QQ 已连接”或“机器人可用”。网络中断、权限不足和凭据错误有独立诊断，恢复不重复创建应用。

### QQ 提示词源码与运行绑定

标准配置继续无需开发账号。单独的提示词改进操作先冻结应用专属源码，保持根内的 BotSpec
及 profile 引用，不生成安装身份或接受回执。开发服务和结果目录按应用及基线隔离，只允许
修改身份与回复提示词。完整接受后由宿主从真实任务导出并正式安装；仅停止状态允许切换，
新版本不自动启动。源码、定义及服务启动配置均须匹配，未知进程状态不重新生成运行令牌。
准备基线不会激活候选，仓库级 Eval/Harness 不因此获得外部应用权限。
具体交付边界见[Studio QQ 提示词交付](../../docs/reference/delivery.md#studio-qq-提示词交付)。

### 源码开发与桌面交付

新项目以无渠道应用和可改写的桌面页面为基线。宿主限定候选的应用提示词和实现目录。新项目只包含当前应用、所需运行源码和宿主提供的应用接口回归。框架自身的回归保留在工作台源码中，由框架的 full 检查执行。每次独立验收生成的 pytest 和 Agent Case 功能测试按摘要保存在受管任务中。后续任务核对前一任务的已验收应用与当前源码一致，再将历史测试冻结到自身证据中，在隔离执行副本里运行全部应用回归；应用源码保持前一版接受回执的精确摘要。应用 worker 的可写范围不包含共享框架或已有测试。明确需求以用户原文冻结，用户确认上一轮讨论时附上同一会话实际显示的讨论内容。工作台冻结自己的开发 worker 与验证服务，目标应用始终使用独立冻结的基线。完整应用仓库回归可按测试文件分给四个隔离进程，仍核对全部冻结用例及其真实结果。受信发布程序从独立验收回执取得精确源码，只将当前应用和所需运行源码编入 Windows 安装包。回执分别绑定完整候选摘要、装入 Windows 的源码摘要和安装包摘要。试用和下载使用同一文件。签发候选、成功构建以及 Windows 实际运行分别取证。普通用户的模型凭据、会话和数据只保存在各自安装中。

既有 Live2D 以明确选择的 Windows 安装的公开清单和实际选中版本为基础。在新的试用目录启动原生桌宠，使用独立的安装身份、端口和数据。目标电脑使用自己的聊天模型，独立运行不依赖工作台或 WSL。

工作台按自身源码摘要保存独立验证快照，验证服务和 socket 同时绑定该快照，每项任务记录原快照摘要，重启和重试继续使用原规则；目标应用的旧评测文件不能替换宿主规则。
Live2D 新需求使用声明式 Agent Case 复用生产 Gateway、实际头像 MCP 和受控浏览器回执，核对工具调用、动作、回执与回复顺序。
验收仍比较冻结基线与候选、独立确认并保护原应用 Suite；通过后才允许网页打包和下载，原生窗口表现另行取证。

## Acceptance

标准应用在无需开发账号、无需编辑文件或执行命令的情况下完成配置与启停；凭据不出现在对话、公开状态和导出物中。配置草案必须确认，重复操作不重复创建进程，失败及重启后可以继续。QQ 配置检查与真实收发证据独立，未进行真实收发时不得显示端到端成功。

桌面开发验收覆盖示例界面与 Agent 工具操作同一份应用数据、两个项目的隔离、重复请求、连续改进、安装包内容核验和真正的 Windows 安装。受控模型、WSL 构建、Windows 启动和另一台电脑上的独立试用分别报告。

## Verification

运行项目与消息隔离、配置提案确认、密钥脱敏、API-only 标准应用、生命周期与错误恢复、QQ 官方渠道编解码和受控投递测试。对工作台检查加载、空、错误、重复点击及窄屏状态；桌面路径继续覆盖示例 MCP、Windows 安装与浏览器测试，并按开发指南执行 full。受控对端不证明真实 QQ 权限、模型效果、平台审核或用户可见交付；这些需要持有有效授权的目标环境另行验收。
