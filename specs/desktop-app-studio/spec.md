# 本机 Agent 应用工作台

## Summary

工作台以“通过对话创建、运行和改进 Agent 应用”为目标，复用现有引擎、接口、Console、Harness 和 Eval，不引入第二套运行体系。Windows 入口启动 WSL2 内的本机工作台。开发对话和每个项目的源码、任务、产物在本机保存。一段对话绑定一个应用，开发请求从该项目的当前版本进入既有 Harness 和 Evaluation。业务应用通过自己的 BotSpec、Agent profile 和 Gateway 运行。

## Design

### 应用中心首版

首版先覆盖已有 NapCat/OneBot QQ 与 Windows 原生 Live2D；所有应用共享同一工作区结构。
客户端负责业务交互，Studio 提供后台记录与模型、人设、回复风格表单。源码身份、开发基线与
内部诊断按需展开。接入已有原生应用只登记连接，不复制应用库或导入开发源码。

原生应用以专用 Gateway 管理身份提供观测及设置，宿主注入现有观测查询和配置服务。
管理身份不获得业务聊天、工具执行或进程控制能力；Windows 回环由按需本机转接访问。
原生端在本系统读取数据库，离线明确显示不可用，不跨系统打开活动 SQLite。
用户提示词保存在私有运行目录；身份与回复风格仍进入原信任分区，不修改交付源码或会话人格。
模型与提示词分别按版本保存，外部变更要求重新读取。保存不自动重启，当前保存与实际加载分别展示。

### 统一应用工作台与渐进整合

工作台顶栏为「我的应用」和「平台管理」。在应用身份栏下按运行监控、质量与改进、
开发与交付、应用配置分组。业务任务与失败测评 Case 可以携带原标识进入修复，宿主在读取
详情和执行操作前核对所属应用。共享连接、模型方案、开发账号、共享服务及项目级全仓熵回收
归平台管理。应用开发助手是 Studio 私有服务，应用目录仅收录用户应用。

新应用通过需求弹窗创建。首版需求、方案修订与确认保存在同一 Studio 项目，讨论不启动开发。
宿主只接受当前修订的显式确认，按确认的交付形态建立源码或配置，然后交给已有的生命周期服务。
接入已有程序是独立操作。网页产物从已接受候选提取，下载与实际运行分别记录。另一本机 Studio 接入该交付时沿用项目、验收任务与构建身份，保存原始安装包并定位已运行的同版本服务。

产品概念分为 AgentStrata 引擎、AgentStrata Studio 工作台、AgentStrata Apps 应用和组件四层。应用类型描述用途，应用实例拥有用户名称、配置、运行与历史；插件、渠道适配器、Skill 和 MCP 工具是实例使用的组件，不因展示命名改变持久标识或协议。Studio 作为统一工作台的产品入口，Console 的 React、Arco 和 Query 前端承载管理界面，逐步纳入创建和改进对话。旧高级入口在迁移期间保留，不通过 iframe 建立第二套控制面。

分阶段实施顺序：

1. 聚合仓库、Studio 与组件暴露的应用，建立带来源的稳定身份、能力和运行引用。相同源码配置路径只出现一次，优先保留拥有控制权的来源；状态来源失败不能变成空的成功列表。
2. 以“我的应用、平台管理”组织统一前端。每个应用有稳定地址，展示概览、使用、配置、记录和改进；操作按能力显式启用，旧入口继续可达。
3. 将支持的配置、检查、启停及管理对话接入统一应用接口，委托既有管理器，不新增运行引擎或双重服务控制。试聊仅在身份和无外部投递边界验证后开放；外部客户端只展示实际可用入口。
4. 用应用身份关联现有记录、Eval 和 Harness，保持候选、独立接受与显式启用。按应用预选的高级入口是渐进整合，不等于所有来源已支持同等的测评与版本管理。

应用目录是薄的聚合视图，不复制 BotSpec 或业务数据。稳定身份由来源与原有 ID 构成；名称不是定位依据。实例引用、管理项目引用和能力独立记录，组件自身不重复作为应用展示。Studio 的标准应用由原 ApplicationManager 管理，仓库实例沿用 Console 的原有控制路径，插件暴露的只读实例不能因新页面得到额外控制权限。

“使用应用”与“改进应用”是不同上下文：前者属于业务 Gateway 会话，后者属于管理项目与开发任务。管理模型只获得用户明确输入及允许的应用配置摘要，不能读取完整私有配置、凭据或环境。前端请求、Query key、草稿与消息均绑定稳定应用身份，切换后迟到响应不能显示在另一应用。进程、渠道连接、端到端交付分别展示；未验证状态不能通过显示名称推断为成功。

### 统一桌面开发入口的迁移

自定义桌面应用与标准 QQ 应用共享 React 工作台和应用身份，但不共享业务会话与开发权限。
保留 Studio 的项目库、源码、任务、冻结验收与打包逻辑，不复制新的 BotSpec 或开发数据库。
本次按以下顺序迁移；前一阶段的兼容验证是切换下一阶段入口的前提：

1. 抽出可由 Console 和旧 Studio 托管的开发任务服务。进程所有权绑定同一项目库，
   同一时刻只有一个消费者；重复请求沿用持久消息 ID，恢复先检查原任务而不是重建任务。
2. 在统一创建页开放桌面项目，将需求对话、开发状态、验收、重试和已验证构建下载纳入应用工作区。
   原项目和历史直接读取，业务使用与源码改进仍分开；QQ 配置装配不需要开发账号。
3. 模型与连接提供开发账号状态及明确授权入口。聊天、开发 worker、测评用途保持独立，
   Console 所选模型文件显式传入开发服务，不另建或覆盖用户配置。
4. Windows 启动器使用统一工作台，构建包含生产前端资源。保留安装身份、
   WSL 用户和数据目录；升级前识别活跃开发任务，不以强杀进程或放宽目录权限完成切换。
   无法识别或为空的任务状态阻止跨版本替换，保留原记录，由原版本完成诊断或恢复。
   跨版本准备或缺少前端资源时，先取得同一项目库的开发消费者锁并持有至就绪证明通过；
   网页服务停止不代表正在收尾的开发线程已经结束。同版本且资源已就绪的再次打开不争抢消费者。
5. 在新装、升级、旧项目、任务恢复和构建交付验证后退出旧页面。迁移期保留兼容入口，
   不能同时运行两套消费者；不因入口合并解开桌面应用启动的安全限制。

启动器的本机令牌兑换为 HttpOnly、SameSite 会话，统一 API 仍须保持原来的认证及同源边界。
固定端口的网页响应不能证明目标工作台就绪。返回启动地址前，使用独立随机挑战核对服务进程
与启动令牌的 HMAC 证明，令牌不随探测发送；Windows 启动器同时核对 systemd 的 MainPID。
探测不使用代理、不跟随重定向、不创建登录会话，旧记录、其他进程或失败探测不得推进版本记录。
安装版使用原 WSL 用户的项目库，源码开发启动的用户目录不隐式合并；跨用户迁移不是本次自动操作。
前端只提交应用和消息身份，不能选择任意源码路径、Shell 命令或自报验收成功。

### Live2D 导入的持久操作

桌面伙伴导入是显式本机操作，不是普通空项目创建。统一入口登记稳定请求 ID 后再调用现有
Windows 来源选择器；选择器只返回安装与载荷来源，HTTP 不接收任意路径。导入状态与
原项目关联持久保存，跨进程加锁，同一请求的重复提交或刷新不能重复弹窗。

选择结果先保存再核对并导入源码。中断后若来源已明确，只允许继续同一来源的验证；
若结果不明则保持恢复待确认，不自动重新选择。已有源码必须与所选载荷匹配，不能以
目录存在代替校验，也不能为重试删除历史。取消、失败、处理中和导入完成分别展示。
导入成功只表示建立了源码开发基线，不表示桌宠运行、安装或功能验收成功。

旧开发任务直接读取原证据；缺任务、冻结验证快照或当前版本不符时只读展示原因，
不生成新的验收回执以恢复旧任务。已验收构建仍走摘要校验后的下载；不将执行已安装
Python 的旧版本观察操作包装成无副作用的只读入口。

恢复检查只读取既有 Harness 元数据及其摘要绑定的来源证据，不初始化空任务库、创建证据目录
或调整旧目录权限。未完成而无法核对的记录保留原状态、需求和答复，不自动消费；所属应用
暂停新的开发以免和未知结果重叠，其他应用继续使用。已失败的旧记录只读保留，不阻止显式新请求。
显式重试重新核对原任务和冻结字节，不能用进程缓存掩盖记录丢失或证据变化。恢复扫描在线程中
运行，消费者退出时等待扫描结束后才释放同一项目库的所有权。

### 应用范围验收

- QQ 工作台试聊使用独立 Gateway user 客户端，工具白名单为空；会话与管理对话、QQ 渠道会话分离，试聊不产生 QQ 投递。旧进程缺少专属凭据时不能退回 owner 身份。
- 试聊使用公共 Gateway run 身份契约；持久请求 ID 不可跨应用或改写内容，未知结果先查询，明确不存在才允许用户用原 ID 重试；终止请求与终态分别显示。
- 仓库应用的 Eval/Harness 历史由服务端解析精确实例身份，筛选先于分页。Studio 仓库外应用不通过放宽源码边界获得这些能力。
- 桌面构建下载复用原产物校验：项目与消息必须匹配、构建就绪、摘要一致。不把下载或打开安装包表述为启动已安装应用。
- 新桌面构建的受信发布程序记录完整启动程序及资源清单，回执绑定清单摘要、安装 ID 和运行源码。统一使用页只能通过固定本机选择器绑定实际安装，核对文件归属、写权限、无重解析点、完整文件摘要与运行版本；校验时持有文件的只读共享句柄。请求不接受任意路径或命令，不因显示名称或历史启动记录推断安装位置。旧构建缺少清单时拒绝绑定。现有准备流程未产出可信的已解包依赖清单，因此启动在 UI、BFF 和原生脚本均拒绝；绑定不等于完整运行环境可信。

### 桌面运行依赖的后续信任条件

启用统一启动前，受信 provisioner 必须从已绑定摘要的 Python 发布归档、wheel、插件和 MCP
下载物派生完整执行文件集合，覆盖解释器、DLL、site-packages、启动脚本、插件运行环境及
生成的路径配置。派生应在全新隔离目录完成，不执行既有安装中的 Python 或复用未经重新
核验的缓存；只允许由可信输入及确定性转换得到的成员，生成项须记录转换版本与输入摘要。
构建/部署回执须将这些结果与 launcher、应用源码、安装身份绑定，用户配置和业务数据
保持独立。启动前同时校验完整成员集合、摘要、路径归属和无额外可加载代码，并处理
依赖更新后的显式重新验收。安装端自行生成的 JSON、artifacts_digest 标记、以及首次绑定
时给现有环境拍摄的摘要都不是独立可信依据。当前未实现该链路，不能宣称统一桌面启动完成。

输入清单基础先从冻结归档的字节派生完整成员事实，不能从现有环境反推来源。受限 ZIP 与
TAR 编译器只提供独立可验证的输入清单，不解包、安装、生成路径配置或签发接受回执。
Python 固定输入声明绑定官方下载表的完整提交、摘要及精确 selector，并单独固定归档
摘要；纯消费 API 要求独立宿主输入锁 pin 并重核整张元数据，基础复制计划使用固定的
内容寻址槽位。基础镜像已支持从原始输入和独立 pin 在新私有目录排他暂存、持有句柄
回读及检测额外成员；失败保留现场，不覆盖、清理或执行解释器，也不签发安装/接受回执。
原有生产 provisioner 尚未消费这些结果。格式、资源预算及验证入口由
[运行依赖输入清单](../../docs/reference/delivery.md#运行依赖输入清单基础)维护。
受限 wheel 的 [Windows 字节安装计划](../../docs/reference/delivery.md#windows-wheel-字节安装计划)
已能推导 site-packages 重定位、跨包冲突和版本化 INSTALLER/RECORD 字节，不执行安装。
独立环境声明已将固定 Python、wheel 集合及 recipe 绑定，原生 Windows 可暂存受限 venv
布局和禁用 site 的路径配置，并从原始输入及前次文件系统身份观察重新验证；Linux 只做
纯计划和适用攻击回归，不能冒充 Windows 文件系统验收。具体范围由
[环境隔离暂存](../../docs/reference/delivery.md#windows-python-环境隔离暂存)维护。
环境 v2 已在落地前校验固定 wheel 的 Python 版本、声明依赖及 extras 闭包，并拒绝
缺项、冲突和无关发行版；v1 保留原有暂存范围。规则及生产接入顺序见
[声明闭包](../../docs/reference/delivery.md#windows-wheel-声明依赖闭包)。
原生载荷生产入口已从冻结源码导出并校验 core/agent host 锁，将根需求与源码、目标 Python 和输入摘要写入已有 artifact/build 绑定；读取时重核确定性声明。host 声明后已能固定精确 Windows wheel 输入；提供完整宿主缓存时先做原始归档与声明闭包审计，再复制单哈希输入供 bootstrap 离线消费。只选定与完整输入审计分别记录，不代表插件/MCP、v2 隔离安装、完整加载路径或 ABI 已验收，见[交付输入](../../docs/reference/delivery.md#固定-windows-host-wheel-输入与离线缓存)。
真实 host 输入现可通过显式 v3 映射隔离启动钩子及原始 data 脚本，转换有前缀/参数检查的 console/gui 入口，并在私有 Windows 目录落地回读。生产构建和读取已绑定映射及 v3 输入，bootstrap 尚未调用 v3 provisioner；见[安装映射](../../docs/reference/delivery.md#windows-wheel-安装映射与隔离入口)。
构建/读取已新增应用、host、launcher、MCP、工具及插件必需作用域，缺项保持 incomplete。独立接受消费契约绑定安装/数据身份与逐作用域证据；私有更新日志支持意图重试、代际比较、未知结果对账及前一版本撤回，尚不执行实际镜像切换，见[接受与更新日志](../../docs/reference/delivery.md#独立运行接受与更新日志)。
隔离 host 安装编排已消费原始输入、外部接受和更新日志，结合持有镜像验证、原子数据选择及持久恢复限制；回滚、故障及自有测试进程退出已由合成输入在真实 Windows 文件系统覆盖，见[隔离安装恢复](../../docs/reference/delivery.md#隔离-host-镜像安装与恢复)。
Python 输入锁 v2 已从固定供应方原始元数据绑定 host/plugin/MCP 三用途，包括 MCP 3.14.7；生产构建、读取与回执强制关联原始元数据和重算报告，删项或重新摘要不能绕过。旧 v1 来源保留原范围，MCP 新用途只开放基础归档数据计划与隔离落地，环境 v1/v2/v3 均拒绝未完成的前缀/加载配方，见[生产输入](../../docs/reference/delivery.md#独立运行接受与更新日志)。
Windows-MCP v2 另绑定原始 Git 源码及 MCP Python 归档，从原始 pyproject/uv.lock 导出完整声明图；完整原始 wheel 可在专用 3.14 数据入口验证 ZIP/RECORD/METADATA 闭包。v3 的显式源码复制配方进一步合并项目、依赖、受限入口和记录，生产构建、读取、scope 和回执重算并绑定布局；只在全新私有实验目录复制与回读数据，不创建执行前缀。插件另以独立来源策略绑定完整需求、原锁全部哈希及固定 CPU URL，原始 wheel 缺项、未准入的源构建及资产继续阻塞。通用 host 和环境 v1/v2/v3 的版本/格式及加载范围保持原限制，bootstrap 只读检查不签发接受，正常新版 MCP/插件准备在供应方构建前继续拒绝，见[MCP 输入](../../docs/reference/delivery.md#windows-mcp-原始归档与依赖闭包)。
真实前缀/入口、应用源码与插件/MCP 完整环境、加载/ABI、生产准入、实际软件更新/回滚和
独立安装接受仍须完成；隔离数据流程不构成运行验收，生产启动门禁保持拒绝。

### 标准应用装配与运行

工作台分开处理配置操作与源码开发。标准应用以现有 BotSpec、Agent profile、模型绑定和 Channel 接口装配；配置、检查、启动、停止不创建 Harness 任务，也不要求开发 worker 认证。新增接口、工具或业务逻辑才进入既有候选与独立验收流程。模型 API 可以服务标准应用；Harness 当前仍使用 Codex 开发 worker，不能从聊天模型已连接推定开发能力就绪。

首个标准应用类型是 QQ 官方机器人，与已有 QQ / NapCat 的 OneBot 渠道分开。渠道只处理官方认证、事件与投递；身份、准入、上下文和 Agent 能力继续按[四层运行时基线](../runtime-four-layer-definition/spec.md)归属，工作台和生命周期管理位于消息链之外。普通用户不接触 YAML，开发者与 UI 使用同一组确定性应用操作，不让对话模型直接生成 Shell 命令部署。

同一页面组合聊天与连接卡。聊天提出名称和回复要求等配置建议，用户明确应用后持久化；AppSecret 由专用表单输入，不进入聊天、模型上下文或导出物。只给模型及前端返回脱敏状态。请求目标固定为当前应用，启动、停止和重试保持幂等；已有项目记录不因增加应用类型而改写或迁移到另一个应用。

用户自行拥有 QQ 平台账号和机器人，并按平台要求配置权限和测试成员。MVP 仅提供本机运行，不创建平台账号、不代办审核、不自动公开上线或云托管。配置检查、进程运行、官方平台确认和真实消息往返分别取证；不能用本地校验或进程存活表示“QQ 已连接”或“机器人可用”。网络中断、权限不足和凭据错误有独立诊断，恢复不重复创建应用。

### QQ 提示词源码与运行绑定

标准配置继续无需开发账号。单独的提示词改进操作先冻结应用专属源码，保持根内的 BotSpec
及 profile 引用，不生成安装身份或接受回执。开发服务和结果目录按应用及基线隔离，只允许
修改身份与回复提示词。完整接受后由宿主从真实任务导出并正式安装；仅停止状态允许切换，
新版本不自动启动。源码、定义及服务启动配置均须匹配，未知进程状态不重新生成运行令牌。
准备基线不会激活候选，仓库级 Eval/Harness 不因此获得外部应用权限。
具体交付边界见[Studio QQ 提示词交付](../../docs/reference/delivery.md#studio-qq-提示词交付)。

### 源码开发与桌面交付

新项目以无渠道应用和可改写的桌面页面为基线。宿主限定候选的应用提示词和实现目录。新项目只包含当前应用、所需运行源码和宿主提供的应用接口回归。框架自身的回归保留在工作台源码中，由框架的 full 检查执行。每次独立验收生成的 pytest 和 Agent Case 功能测试按摘要保存在受管任务中。后续任务核对前一任务的已验收应用与当前源码一致，再将历史测试冻结到自身证据中，在隔离执行副本里运行全部应用回归；应用源码保持前一版接受回执的精确摘要。应用 worker 的可写范围不包含共享框架或已有测试。明确需求以用户原文冻结，用户确认上一轮讨论时附上同一会话实际显示的讨论内容。工作台冻结自己的开发 worker 与验证服务，目标应用始终使用独立冻结的基线。完整应用仓库回归可按测试文件分给四个隔离进程，仍核对全部冻结用例及其真实结果。受信发布程序从独立验收回执取得精确源码，只将当前应用和所需运行源码编入 Windows 安装包。回执分别绑定完整候选摘要、装入 Windows 的源码摘要和安装包摘要。试用和下载使用同一文件。签发候选、成功构建以及 Windows 实际运行分别取证。普通用户的模型凭据、会话和数据只保存在各自安装中。

既有 Live2D 以明确选择的 Windows 安装的公开清单和实际选中版本为基础。在新的试用目录启动原生桌宠，使用独立的安装身份、端口和数据。目标电脑使用自己的聊天模型，独立运行不依赖工作台或 WSL。

工作台按自身源码摘要保存独立验证快照，验证服务和 socket 同时绑定该快照，每项任务记录原快照摘要，重启和重试继续使用原规则；目标应用的旧评测文件不能替换宿主规则。
Live2D 新需求使用声明式 Agent Case 复用生产 Gateway、实际头像 MCP 和受控浏览器回执，核对工具调用、动作、回执与回复顺序。
验收仍比较冻结基线与候选、独立确认并保护原应用 Suite；通过后才允许网页打包和下载，原生窗口表现另行取证。

## Acceptance

标准应用在无需开发账号、无需编辑文件或执行命令的情况下完成配置与启停；凭据不出现在对话、公开状态和导出物中。配置草案必须确认，重复操作不重复创建进程，失败及重启后可以继续。QQ 配置检查与真实收发证据独立，未进行真实收发时不得显示端到端成功。

桌面开发验收覆盖示例界面与 Agent 工具操作同一份应用数据、两个项目的隔离、重复请求、连续改进、安装包内容核验和真正的 Windows 安装。受控模型、WSL 构建、Windows 启动和另一台电脑上的独立试用分别报告。

## Verification

运行项目与消息隔离、配置提案确认、密钥脱敏、API-only 标准应用、生命周期与错误恢复、QQ 官方渠道编解码和受控投递测试。对工作台检查加载、空、错误、重复点击及窄屏状态；桌面路径继续覆盖示例 MCP、Windows 安装与浏览器测试，并按开发指南执行 full。受控对端不证明真实 QQ 权限、模型效果、平台审核或用户可见交付；这些需要持有有效授权的目标环境另行验收。

统一入口按上述五阶段依次收口，验收仍使用既有服务与回执：

| 阶段 | 必须核对的行为 | 实际验收边界 |
| --- | --- | --- |
| 1 任务管理 | 同一项目库的新旧入口只消费一次持久请求；原消费者退出后交接，重试不换应用或内容 | 隔离 API、SQLite 和真实进程锁可验证所有权；受控开发步骤不能证明真实模型任务完成 |
| 2 桌面工作区 | 原项目与历史直接可见；创建、需求、开发、独立验收、打包下载关联同一应用；业务聊天隔离 | 下载测试核对原摘要及跨应用拒绝；真实交付另须执行完整 Harness/Eval、独立接受与 Windows 构建 |
| 3 模型和账号 | 同一模型文件传入工作台与开发服务；聊天、开发和测评分别绑定；QQ API 配置不要求开发登录 | 状态和授权路由测试不代替用户账号登录、模型可用性与实际费用授权 |
| 4 Windows 入口 | 生产 React 资源可构建；保留原安装身份、WSL 用户、项目目录；活跃消费者、任务或未知状态阻止准备 | 隔离命令与锁测试不代替真实新装或升级；应在明确的隔离目标核对旧项目、失败恢复和版本记录 |
| 5 旧入口退出 | 新装、升级、旧项目、任务恢复及构建交付逐项留证后再退役旧页面 | 前述真实目标环境验收缺项时继续保留兼容入口和原启动安全限制 |
