# 领域内部六层源码依赖基线

## Summary

AgentStrata 已有四层运行时职责基线和跨领域静态依赖检查，但尚未统一各业务领域内部的
源码分层规则。本规格将 **Types → Config → Repo → Service → Runtime → UI** 固化为
全项目各领域内部的硬性开发规则，并作为该规则的唯一权威定义。

本次交付为规范和入口引用，不包含业务代码重构、数据迁移或六层自动检查器。公开 API、
运行行为和数据格式保持不变；`accepted` 表示规则已接受，不表示全仓存量已完成迁移。

## Design

### 适用范围与方向

规则适用于全项目各业务领域的新增模块、新增依赖和结构性修改。存量按本次改动涉及的
职责和依赖逐步调整，不因本规格启动全仓重构，也不能以存量为由继续新增违规依赖。

**Types → Config → Repo → Service → Runtime → UI** 表示从基础到上层的排列顺序。
实际源码依赖由使用方指向被依赖方：右侧层只能依赖下表获准的左侧层，禁止左侧反向
依赖右侧，禁止循环依赖。允许跳层，不要求调用依次经过全部六层；下表约束跨层依赖，
同层协作也必须符合职责边界且不得形成循环。

### 职责与允许依赖矩阵

| 层 | 职责 | 领域内部允许依赖 |
| --- | --- | --- |
| Types | 数据类型、错误、端口协议与纯校验；不读取环境或执行数据 I/O | 基础类型及纯共享契约 |
| Config | 配置读取、解析、校验与确定的配置快照；不承担业务数据持久化或运行对象装配 | Types |
| Repo | 数据及证据读写、事务和完整性；不决定业务用例或管理 worker 生命周期 | Types、Config |
| Service | 业务用例、状态流转与业务判定；通过端口使用外部执行能力 | Types、Config、Repo |
| Runtime | 对象装配、连接、进程及 worker 生命周期 | Types、Config、Repo、Service |
| UI | CLI、Console 的输入、展示与操作映射 | Types，以及公开的 Service／Runtime 控制和查询入口 |

基础库和共享模块仍需符合使用层的职责与项目既有依赖约束。不能借助通用 helper、
包重导出或函数内导入绕过边界；文件名不决定职责归属。

### 端口、公开入口与领域边界

- 端口协议归入 Types，具体实现由 Runtime 装配注入。Service 依赖端口，不反向导入
  Runtime、具体 worker 或执行适配器。跨领域共享 DTO/ports 继续使用现有 contracts。
- UI 通过公开服务操作业务，不直接访问业务数据库、Repo 实现或具体执行适配器。
  允许调用公开 Runtime 控制和查询入口，不代表 UI 可以自行创建 Agent、模型连接或
  承担宿主装配职责；Console 继续遵守现有控制观测边界。
- 六层规则约束领域内部；跨领域调用同时遵守四层运行时基线、现有领域依赖规则与
  公开契约。目标处于更基础的层，并不自动授予跨领域访问权限。
- 按实际职责划分模块，不强制每个领域建立六个目录，不为凑层数增加空壳类、通用基类
  或另一套注册与装配框架。

### 与四层运行时基线的关系

本规格与 [四层运行时基线](../runtime-four-layer-definition/spec.md) 同时生效。
**Channel → Gateway → Application → Agent** 描述消息处理职责和结构化交接；六层
描述各领域内部的源码组织与依赖方向，两者不要求一一对应。

Channel 的事件与投递、Gateway 的身份准入与交付协调、Application 的 actor/工作区/
上下文与交换、Agent 的模型与工具执行继续遵守原有职责和交接契约。启动装配、实例宿主、
Console 和 Evaluation 仍是四层之外的配套部分；六层中的 Runtime 不新增消息必经层。

### SDD 约束与当前执行方式

涉及领域内部架构或依赖结构变更的 SDD 必须引用本规格，并在已有 `Design` 章节说明
受影响职责、依赖方向和公开入口；涉及运行时的设计同时引用四层基线。普通修复沿用
[SDD-lite](../../docs/maintenance.md) 的范围，不增加固定审批表、元数据字段或顶层章节。

当前通过规范与评审执行六层规则。现有 [架构检查器](../../scripts/check_architecture.py)
检查跨领域依赖、专项边界与循环，尚未全面检查领域内部的六层职责及依赖矩阵。
检查器通过不等于全仓六层合规；代码迁移和自动检查覆盖范围留待后续任务明确。

### 正反例

以下箭头均表示“使用方依赖被依赖方”，不是从基础到上层的排列顺序。

| 示例 | 判定 | 原因 |
| --- | --- | --- |
| `Service → Repo` | 合法 | 业务用例通过数据访问层读写业务数据 |
| `Service → Types` | 合法 | 可跳层使用 DTO 或端口，无需经过 Repo、Config |
| `Runtime → Service`，并注入符合 Types 端口的实现 | 合法 | 装配和生命周期由 Runtime 负责 |
| `UI → Service` 的公开查询入口 | 合法 | UI 通过公开契约获取展示数据 |
| `Repo → Service` | 不合法 | 数据访问层反向依赖业务层 |
| `Service → Runtime` 或具体 worker/执行适配器 | 不合法 | 业务层穿透到运行编排或具体执行实现 |
| UI 直接读取业务数据库或调用 Repo | 不合法 | 绕过公开服务与业务规则 |

## Acceptance

- SDD 与架构入口均引用本规格，完整职责矩阵和依赖方向以此处为准。
- 规则明确覆盖全项目各领域的新增模块、新增依赖和结构性修改；不宣称存量已全量合规。
- 评审可据矩阵与正反例判断合法跳层、反向依赖、端口注入和 UI 绕过公开入口。
- 四层运行时职责、交接和跨领域边界继续有效；六层规则不将配套部分变成消息必经层。
- 本次差异只包含规范与入口引用，未改变业务代码、公共 API、运行行为或数据格式。
- 格式检查和现有架构检查的通过与六层代码迁移、自动检查完成分别陈述。

## Verification

- 结构与格式：使用 `git diff --check` 和 `.venv/bin/python scripts/check_sdd_specs.py`。
- 规则一致性：核对两个入口均引用本规格，职责矩阵、正反例与四层运行时基线一致。
- 仓库回归：按 [开发与验证约定](../../docs/guides/development.md) 选择相关检查；现有
  `.venv/bin/python scripts/check_repo.py fast` 包含静态检查与日常回归，但不证明全仓六层合规。

单次执行日期、测试数量、耗时和临时故障记录放在交付说明或 CI 日志中，不写入本规格。
