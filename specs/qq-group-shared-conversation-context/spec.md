# QQ Group Shared Conversation Context

## Summary

QQ group messages use one conversation scope per stable group ID instead of one scope per sender. Members of the same admitted QQ group share bounded conversation history and one user-visible workspace, while different groups, QQ private chats, and other platforms remain isolated. Every accepted turn still carries the stable current sender and transport source separately; sharing a conversation never shares an Owner-private authorization context.

The deployed cc-connect version provides both a shared QQ group session key and a sender envelope on every forwarded message. AgentStrata enables those capabilities together and cross-validates the envelope against an independently written `message.received` hook record in a bounded, locked per-session attestation queue at the ACP prompt boundary. Each record has an independent random ID and is consumed exactly once, so queued or repeated same-body messages do not overwrite one another. Missing, stale, unsafe, actor/body-mismatched, or cross-group evidence fails closed. Display names are descriptive only. QQ admission and roles continue to use the stable sender ID. This transport claim has been checked against the pinned cc-connect source and rendered configuration; a real two-account QQ ingress round trip remains an explicit deployment acceptance step.

## Design

`PlatformAdapter` declares whether a group conversation is scoped by actor or by chat. Existing adapters default to actor scope. QQ declares chat scope, renders `share_session_in_channel = true`, and requires project-level `inject_sender = true`. The shared cc-connect key `qq:g:<group-id>` normalizes to a group conversation with no sender. A synchronous `message.received` hook appends the real transport actor and original user-body digest to a bounded JSON queue in an instance-private `0700` directory; the exact session key is represented only by SHA-256 state/lock filenames, and both files are securely opened as single-link mode-`0600` files. State updates and ACP consumption share an inter-process lock. Before comparing that digest, ACP converts only complete terminal file/image suffixes added by cc-connect into resource references, then parses the sender envelope; the canonical remaining body must match one live random-ID record. That exact record is removed atomically while stable conversation identity remains available to the wrapper. A user-authored suffix remains covered by the hook digest and therefore cannot become trusted attachment evidence. A second envelope-looking line inside user content is ordinary untrusted text. Missing, malformed, stale, unsafe, wrong-platform, wrong-group, actor/body-mismatched, or identity-free evidence is rejected before ACP admission, attachment handling, tool dispatch, model execution, or journal mutation. The wrapper never sources this file as shell code.

Conversation identity and turn identity are distinct contracts. Conversation identity contains `platform`, normalized `chat_kind`, and stable `chat_id`. Turn identity contains the current stable sender ID, optional display name, ACP message ID when available, and the trusted transport source. Reply or quoted-message authors are not inferred when the transport does not provide them.

QQ group workspaces use `<workspace-root>/group_<safe-chat-id>/shared/`. The parent is never the user-visible workspace because it can already contain legacy `user_*` directories and protected group metadata. Existing `group_<id>/user_<id>/` directories remain in place, are not merged automatically, and cannot be traversed from the shared root. QQ private chats retain `p2p_<safe-user-id>/`; non-QQ group adapters retain their current actor-scoped layout. The member-writable shared root has no authoritative `IDENTITY.json`; stable conversation and actor identity stay in runtime contracts and protected sibling state, so no sender can replace control metadata with a symlink or become the apparent workspace owner.

The current QQ group workspace shares ordinary conversation files and explicitly group-bound attachment/result files. It does not expose credentials, backend state, job control records, or any authoritative memory or persona file beneath the member-writable `shared/` tree. Group memory and group persona are separate protected persistent-state scopes selected from trusted conversation identity. All admitted group actors receive the current group memory and Owner-managed group persona; all may read and append group memory, while only an authenticated Owner may clear it or receive the main-session `persona_manage` projection. User/Admin turns cannot see the tool, read raw persona, or mutate any persona scope.

Authorization remains actor-scoped and channel-independent. Before every accepted prompt, middleware resolves the real sender and selects an actor-bound execution session whose workspace service, permission filter, file sender, backend caller identity, and protected execution state are bound to that sender and the shared root. A stable sender configured as Owner remains `Role.OWNER` in both private and group chats; User/Admin actors retain their own roles. Group admission never promotes a member. Owner group turns receive the ordinary Owner prompt and tool projection, while User/Admin group turns receive the member-safe projection. Speaker changes cannot transfer Owner tools, Codex worktree access, credentials, task ownership, or backend caller identity.

Conversation sharing does not mean sharing privileged backend scratch state. The protected journal contains only accepted group-visible user/assistant exchanges with actor/source attribution. Raw privileged tool results, relay credentials, Codex runtime state, and other execution internals remain under actor-scoped protected state and are not copied into another actor's backend. Owner group tool payloads still use a group-audience sanitizer before reaching the model or persisted group-visible artifacts. The protected current-group memory is projected as untrusted historical data, but private-chat memory and private Wiki/RAG are never projected into a group turn; explicit tools remain governed by the actual sender role and any tool-level channel restriction.

Owner group background jobs use an actor-scoped protected jobs directory below `.conversation-state/`, never `shared/jobs`. The request, status, result, notification, and logs therefore cannot be forged or read through ordinary shared-workspace tools. Notifications may target the originating group, but lookup, cancellation, resume, and replay remain bound to the authenticated Owner actor. Every inbound group message must obtain a Console observability record before admission, attachment, model, or tool side effects; if safe task persistence is unavailable, the turn fails closed. Messages with authenticated actors write below `.conversation-state/task-actors/<actor-digest>/tasks/`, including access-denied terminal records, but denied actors never receive an execution session. The digest binds the stable conversation and authenticated actor without exposing the raw actor ID in a path. An admitted task stores the bounded, observability-redacted canonical current user body in its summary/turn record so Console can diagnose the actual request. Model-context history, subagent transcripts/results and delegated-job free-text remain omitted. Admission-denied and invalid-admission-config tasks keep only their generic replacement text. Identity-invalid messages write only a generic failed record below `.conversation-state/task-intake/tasks/`; raw message text, sender envelope, actor ID, and any actor reference left on the shared session shell are not persisted there. All of these records remain outside the member-writable `shared/` root. They are operator diagnostics: Console may discover them, while shared-group task tools remain denied and group members cannot read them through workspace tools.

The conversation layer persists accepted exchanges in a mode-`0600` JSONL journal under the protected sibling directory `group_<safe-chat-id>/.conversation-state/`. Paired protected metadata binds an epoch, monotonic sequence high-water mark, retained range, record count, and journal digest. A missing pair member, deletion after initialization, single-file parseable truncation or restoration, or cursor ahead of the durable high-water mark fails closed and invalidates every cached actor backend for that group session; append never silently restarts at sequence 1. Each live journal instance also remembers the last valid epoch, generation, and digest it observed, and rejects a subsequently observed internally valid pair that regresses or changes at the same generation. A coordinated byte-for-byte offline rollback of the entire protected state domain before a new process starts cannot be detected without an external monotonic anchor; the current design does not provide one and does not claim that guarantee. Records contain the journal epoch and sequence, message ID when available, the raw stable actor and transport source required for authorization/audit, bounded user text, bounded assistant text, and timestamp. Append first applies the record-count bound, then drops oldest records until the actual serialized UTF-8 journal fits its byte bound; if the newest record alone does not fit, or the paired metadata would exceed its bound, it rejects the append before replacing either durable file. The raw actor is never treated as a display label or model-granted role; model-visible history uses a conversation-scoped actor reference. Access-denied or invalid-identity messages are not appended. The current actor's live execution session receives a bounded, explicitly untrusted snapshot or delta of the group journal plus a runtime-authored current-source appendix. Native backend identity, transcript, and Codex state remain actor-scoped beneath the protected state directory, but shared-group Codex does not restore a persisted native thread after actor-cache eviction or process restart because the corresponding journal cursor is intentionally process-local; it starts a fresh thread from the bounded journal instead. Live turns on the same materialized actor session still use native resume. Group context is shared through the journal rather than by reusing another actor's backend authorization session.

QQ shared-group Codex is a separate fail-closed isolation profile. Bubblewrap exposes only the exact shared root as read-only, clears inherited environment, and hides workspace `.codex` configuration and project instructions. If `<shared>/.codex` does not exist, the runtime does not create a mount point because the read-only parent already prevents Codex from creating project configuration. If it exists, only a current-user-owned, non-symlink real directory may be overlaid with tmpfs; a file, symlink or unsafe owner fails closed. It maps the current actor's gateway configuration read-only and the actor's isolated Codex runtime home separately; host-owned native-resume/session and audit control records are not mapped. Codex's direct shell, `apply_patch`, app/plugin, and other write-capable built-ins cannot modify the shared tree. Every permitted shared-file mutation must cross the actor-bound, workspace-scoped Session Gateway MCP and be re-authorized and containment-checked on the host. Missing bubblewrap, invalid protected paths, or a non-unique gateway configuration aborts session creation; the runtime must not fall back to an unisolated group Codex session.

The cc-connect static `default/.cc-connect/attachments` inbox stores only a basename and contains no chat or message identity. A shared-group turn therefore fails closed instead of importing from that ambiguous legacy inbox. It also refuses to treat a same-named file already in `shared/.cc-connect/attachments/` as proof of the current upload. The rejected turn is recorded once with a stable explanation and does not schedule a misleading delayed acknowledgement. Files already inside the current group's shared workspace remain usable as ordinary shared data through explicit workspace discovery; validated inline resources that are intrinsically bound to the accepted ACP turn retain their existing path.

The ACP group-session lock serializes turns in one process, and journal append uses an inter-process file lock. A cached actor session advances its journal cursor only after the corresponding exchange is persisted. On process restart, a bounded journal snapshot restores group context. Disabling QQ chat scope rolls routing back to actor scope without deleting either the shared directory, protected journal, or legacy actor directories.

## Acceptance

- Two accepted users speaking sequentially in the same QQ group resolve to the same `group_<id>/shared/` root and can use the previous member's bounded conversation context.
- Every stored group exchange retains the actual stable sender for authorization/audit, while model-visible context identifies that sender with a conversation-scoped runtime-derived actor reference; display names never grant a role.
- The same user in two QQ groups, or in a QQ group and private chat, receives different conversation history, workspace, transcript, backend state, and journal.
- QQ private chats and non-QQ platform workspace behavior remain compatible.
- A missing or mismatched sender envelope or private queued hook attestation fails closed before access checks with sender data, attachment handling, tool execution, model execution, or journal append. Concurrent append/consume and repeated same-actor/same-body records remain independently consumable; a user-authored first-line envelope cannot impersonate another actor or pass an old no-`inject_sender` configuration.
- Complete cc-connect file/image suffixes are converted to resource references before body-digest comparison, so a genuine wrapped upload retains the original user body while a user-authored fake suffix cannot satisfy attestation. This normalization does not authorize the ambiguous static group attachment inbox.
- An authenticated Owner group turn remains `Role.OWNER`, receives the Owner prompt/tool/Codex projection, and keeps the same group-shared user-visible workspace. User/Admin turns receive the restricted member projection. Speaker changes do not reuse another actor's executor, caller identity, protected jobs, or Codex authorization state.
- The shared root cannot traverse or inventory legacy `group_<id>/user_*` directories, and no automatic migration copies legacy user data into the shared group.
- The member-writable shared root contains no authoritative identity metadata; protected/runtime conversation identity cannot be replaced by the last sender.
- Accepted shared-group turns create private actor-scoped Console diagnostics outside the shared root and retain only the bounded/redacted canonical current request text in task summary/turn fields; historical model context and subagent/delegated free-text remain omitted. User/Admin cannot discover or read these artifacts through group task or workspace tools. Private memory, private Wiki/RAG projection, and all persona mutation remain unavailable to User/Admin. Protected group memory applies to every admitted group turn and may be read or appended by every admitted actor; only Owner may clear it. Existing generic group persona applies to every group turn; Owner manages it through the Owner-only main-Agent `persona_manage` tool at group scope, while the handler rechecks trusted identity and protected state.
- Owner background jobs store their entire control plane in protected actor state. User/Admin cannot discover, query, cancel, resume, replay, or tamper with those jobs through the shared workspace.
- Identity-invalid and access-denied messages do not enter the group journal or create job records. Both create Console task records before returning: access-denied messages use the authenticated actor partition without materializing execution state, while identity-invalid messages use the protected intake partition and persist no raw message, actor identity, or stale actor reference from a previous accepted turn. Concurrent accepted turns append unique ordered journal records without pairing one sender with another sender's text.
- Deleting both pair members after initialization, removing one pair member, changing only one file to an older or truncated snapshot, presenting an actor cursor ahead of durable history, or showing a live journal instance a pair older than one it already observed fails closed and discards all cached actor backends for that group session; sequence never silently restarts. Coordinated offline rollback of the complete protected state domain across process restart remains outside this contract unless a future design adds an external monotonic anchor.
- Journal bounds are enforced against the actual serialized UTF-8 bytes. Oldest records are pruned first; a newest record or paired metadata that cannot fit is rejected before either existing pair member is replaced.
- QQ shared-group Codex has no direct write-capable builtin path to `shared/`; permitted mutations pass only through the current actor's scoped MCP, and a missing isolation boundary fails closed.
- The ambiguous static cc-connect attachment inbox is never imported into a QQ shared group, and an existing same-named file is never claimed as the current upload. The rejection is journaled once without scheduling a delayed acknowledgement; already group-bound ordinary files remain discoverable through the shared workspace.
- Rendered QQ cc-connect configuration enables shared channel sessions, sender injection, and the synchronous transport-attestation hook for the pinned cc-connect release. Every managed systemd start renders the current BotSpec configuration before starting cc-connect, so a stale pre-attestation config cannot be loaded after a restart.
- No real QQ account, sender, group ID, credential, or machine-private path is added to tracked files.
