# 维护社区贡献

社区以应用需求为入口，共同改进接入、自有 Agent 能力和验证依据。面向贡献者的认领、首次 PR、AI 使用与审查规则只维护在[贡献指南](../../CONTRIBUTING.md)；本页供维护者执行任务整理与社区运营。
技术阶段和完成状态只由[主计划](../../specs/application-harness-framework/spec.md#自有-agent-能力优化路线)维护，Issue 引用相应目标，不复制第二套路线图。

## 准备可认领任务

先定位问题：外部接口缺能力进入桥接或工具；接口可用但选错工具、参数或资料，检查 Agent 能力、上下文与策略；结果无法确认时先完善诊断和证据。仅因现象出现在 Live2D 或 QQ，不足以决定修改适配器。

使用[贡献任务模板](../../.github/ISSUE_TEMPLATE/contribution.yml)，开放认领前补齐目标、交付、源码入口、相似实现、建议做法、准确命令、证据层级、验收和维护者。预计工时是估计，不是对新人的完成承诺。
真实模型或外部执行是必要条件时，提前明确环境、费用与验证负责人；普通文档和局部修复不要求实验设计。

| 标签 | 使用条件 |
| --- | --- |
| `good first issue` | 做法基本确定；项目新人可独立完成；不需要生产账号、私有配置或付费模型；已有可用验证入口 |
| `help wanted` | 范围已收敛，适合有相关经验的开发者；说明必要环境和维护者支持 |
| `area:integration` | Channel、Gateway 客户端、MCP 与外部工具接入 |
| `area:agent` | 能力装配、工具发现、上下文、自有执行与委托策略 |
| `area:eval` | 复现、题目、评分、结果比较与验证基础设施 |
| `area:console` | 操作、诊断与证据呈现 |

复用既有 `bug`、`enhancement`、`documentation` 等类型标签。贡献标签由维护者核实后添加，模板不自动添加。无证据的疑似问题先调查，已有测试覆盖的行为不为凑任务重复补测。

启动任务池目标为 6 项：2 项文档与操作、2 项已复现的局部修复、1 项接入示例或复现、1 项自有 Agent 基线或有依据的改进。条件不够时少发布。之后维持约 6–8 项有效任务，同时深度辅导不超过 3 个新人任务；这些是容量目标，不是自动拒绝规则。

## 任务与技术路线衔接

- A 的任务帮助复现、核对现有覆盖与实际缺口；基线满足需求时接受“无需改动”的结论。
- B 的任务只针对已确认缺口，先明确 Agent 侧改进变量，再比较效果。
- C 的真实 Harness 任务、独立接受与隔离实例验证由维护者组织，普通 PR 不承担完整 M7 门槛。
- D 由控制流程问题触发；不要求先完成其他所有优化，也不预设新增规划节点或重写循环。

已有工具选择、相似工具、不可用、错误恢复、上下文修正和证据选择场景的入口见[主计划基线入口](../../specs/application-harness-framework/spec.md#现有实现与基线入口)。候选不能修改本轮冻结评分来证明自身有效；模型或工具更换的收益不能归因于 Agent 代码。

## 维护认领与审查

使用 Issue assignee、关联 PR 和 PR 自身状态表达进展，不另建任务状态机。推荐任务查询同时筛选开放、贡献标签、无人认领与无关联 PR。每次推荐前人工检查任务是否仍然有效，避免已实现或被本地未发布工作覆盖。

维护者确认认领后指定负责人；有 Draft PR 表示开发中，Ready for review 表示等待审查，合并后关闭对应任务。认领释放、反馈目标与 AI 协作规则沿用[贡献指南](../../CONTRIBUTING.md#找任务与认领)。环境或基线失败由维护者帮助定位，不让新人反复猜测。

审查检查问题是否得到解决、验证是否相称、许可与文档是否齐全。普通 PR 走常规 CI；涉及 Agent 效果才审查可比条件与归因。合并说明具体改善，推荐一项相邻任务，保留作者与原项目署名。持续参与者可先协助复现、答疑和审查，权限授予单独决定。

## 社区入口与内容

| Discussions 入口 | 用途 |
| --- | --- |
| [Q&A：接入与使用问答](https://github.com/Ling-ye/AgentStrata/discussions/categories/q-a) | 应用、目标、接口和可投入范围；明确任务后创建 Issue 并相互链接 |
| [Show and tell：作品与接入展示](https://github.com/Ling-ye/AgentStrata/discussions/categories/show-and-tell) | 支持版本、安装入口、复现方法、验证范围、限制与维护人 |
| [Announcements：项目动态与贡献招募](https://github.com/Ling-ye/AgentStrata/discussions/categories/announcements) | 当前重点、可认领任务及已核实的贡献成果 |

保留 Question Issue；复现 Bug 和明确开发任务进入 Issues。重要决定落回 Issue 或领域文档。轻量示例可进入主仓，维护成本较高的独立应用可独立托管并链接，不因展示自动承诺长期支持。

中文为主，英文入口保持简短。图文以掘金为首轮试验渠道，每两周一篇；每月从已有演示复用一次 B 站短视频。相关上游社区只分享符合其规则的案例或修复。每篇内容连接一个明确参与动作，不批量跨社区发布。

选题依次包括应用接入、工具选错、上下文更新、改动如何验证。机制说明与真实效果分别表述，未取得证据时不写优化结论。维护者使用当前 README 的定义与场景，M7 等完成状态只链接主计划。

## 时间与复盘

每周约 4 小时：两次各 60 分钟答疑与审查，45 分钟任务整理，45 分钟内容与案例，30 分钟指标和机动。人工贡献优先得到回应，依赖机器人 PR 集中处理。审查积压时减少新招募，先完成已有反馈。

启动后的前两周打通入口、模板、任务池与 Discussions；第 3–6 周复盘真实首次贡献并整理应用问题；第 7–12 周形成社区接入成果并按已确认缺口推进能力改进。实际完成情况留在社区更新和运营记录，不把本页改成执行流水。

| 指标 | 试运行目标与口径 |
| --- | --- |
| 外部贡献 | 90 天争取 5 位外部贡献者、8 个合并的人工 PR；排除维护者和机器人 |
| 重复贡献 | 争取 2 人在首个合并 PR 后 30 天内再次合并；只统计有完整观察窗口的人 |
| 应用价值 | 争取 2 个社区接入或扩展示例，至少一个由非作者复现 |
| 能力反馈 | 保留可复核基线与真实缺口；无缺口时记录无需改动，不强行生成补丁 |
| 维护成本 | 记录回应与审查中位时间、放弃原因、待审数量和每周投入，目标为 3–5 小时 |

以上是试运行目标，不是增长或服务承诺。M7 按既有验收证据判断，不以 PR、Star 或演示数量替代。
每周查看 GitHub Traffic，运营记录保存在维护者的私有记录中；Traffic 只保留近期窗口，不把各周独立访客简单相加，也不将来源变化直接归因于 Topics。

访问后无人认领时检查任务价值和入口；认领后没有 PR 时检查环境和隐藏依赖；PR 积压时优先审查；首个 PR 后无人返回时检查成果使用、反馈与相邻任务。默认不设置按 PR 数量发奖、付费推广或赏金，不增加独立社区调度服务。
